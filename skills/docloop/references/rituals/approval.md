# 仪式 · 报批草案（实施方案 / 测试分析 / 验收方案）

用户要"实施方案、实现草案、报批计划、测试分析、验收方案"时读本文件。机制立场见 truth 的 approval 章：**树给人读，账给机器对**；正确性锚在"叶子 ⟷ covers 条目一一对应"，不锚在树的形状。

## 让位条款（先看这条）

流程门禁（何时出方案、批后才执行、RIPER 阶段、证据验收）归 sdd-riper——装了它就按它的流程推进，本文件只管**表达与落点**；没装时本文件独立成立。目标项目 AGENTS.md 落点映射段加一句"任务包/报批草案的表达按 docloop approval 契约"完成缝合。

## 流程（既有机制组合，不开新文档类）

1. **起草总览**：就是一个普通任务包 T-###，Done Contract = "获批 + 内容分流完成"。
2. **CH 裁决**：获批 = 裁决通过，审批人 = 裁决人（有名有姓）。未裁决不开工。
3. **获批后分流**（不变量：总览不许长期存活成第二真相）：形态定论经该 CH 改写进 truth；树叶分进各实施 T（挂 covers）；总览随迭代冻结进 past/。

## 表达契约

草案要让审批人 1 分钟内回答六问：**最终改成什么样 · 具体改哪些部分 · 每个需求点在树的哪个叶子 · 每个叶子由什么测试验证 · 哪些需求未覆盖 · 为什么测试全绿足以证明完成**。

- **改造后形态用图不用大段文字**：模块结构 / 数据流用 `flowchart`、生命周期用 `stateDiagram`（mermaid：GitHub 原生渲染、可 diff、代码块不计 lint 信号）。一图一事；节点只放名词，长句留给树叶；没有形态变化就不画——图管形状，树管验收。
- **测试分析 = 嵌套列表树**（不用 `├─` 字符画）：中间节点（能力域 / 功能）只分类命名，层级按业务语义组织；叶子三行版——「关注 / 验证 / 条目」各一行，关注与验证成对，条目挂 covers ID（行内代码）；未覆盖需求显式列"缺口"分支。
- **附录 = 追溯矩阵**：叶子 → 自动化用例 → 执行证据，机器追溯不挤占主阅读面。
- 中间节点写成长段落、一个验证句背多个需求、缺口静默消失——都是返工信号。

## 格式样例

```markdown
## 测试分析（S-01）

- **数据来源与展示位置**
  - 唯一来源
    - 关注：多个展示区域由同一份配置派生
    - 验证：条目身份与顺序同源
    - 条目：`S-01.R-004`
  - 排重
    - 关注：已进优先区域的条目不重复展示
    - 验证：按稳定身份排除、同标题不同条目不误删
    - 条目：`S-01.R-006`
- **缺口（本批未覆盖，显式留痕）**
  - 多语言文案适配——无裁决、无用例、无证据；条目：未分配

## 附录 · 追溯矩阵

| 叶子 / 验证点 | 条目 ID | 自动化用例 | 执行证据 |
| --- | --- | --- | --- |
| 唯一来源·身份顺序同源 | `S-01.R-004` | `t_source_identity` | run-0728 #12 通过 |
| 缺口·多语言文案适配 | 未分配 | 无 | 无 |
```

## 提交前自检

- [ ] 六问逐一有答案（答不上的那问对应的段落重写）
- [ ] 叶子集合 ⟷ covers 条目一一对应；缺口显式
- [ ] 中间节点无长段落；图只画影响审批的
- [ ] 体积在任务包预算内（250 行）；装不下按"流程"第 3 步提前拆实施 T，不压缩成密段落
