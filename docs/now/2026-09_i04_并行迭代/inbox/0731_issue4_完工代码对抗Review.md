# issue #4 · 建议增加“实现完成后的独立代码对抗 Review”门禁

- 作者：yiqingnian28 · 2026-07-31T07:54:06Z · https://github.com/yiqingnian28/docloop/issues/4

## 背景

当前流程对实施方案审批、测试追溯和验收证据已有清晰约束，但实现完成后缺少显式的独立代码对抗 Review 门禁。

方案本身可行，不代表最终实现一定等价。实现阶段仍可能引入方案偏离、异常语义错误、边界遗漏、资源清理缺失，以及测试假阳性或跳过被误报为通过等问题。

## 建议

在“生产代码与测试实现完成”和“最终验证、真相回写或发布结论”之间，增加一次独立上下文的代码对抗 Review：

1. Reviewer 不继承实现者的对话上下文，只接收获批方案、变更单、验收矩阵、实际 diff 和必要代码入口。
2. Review 只读，目标是证伪“实现与获批方案等价且证据有效”，不复述优点，也不直接修改代码。
3. 至少核验：
   - 实现是否偏离获批方案或遗漏验收条目；
   - 异常传播、重试、中断、资源清理和并发边界；
   - 配置边界、框架契约和横切行为；
   - 测试是否存在 mock 掩盖、无效断言、误跳过、环境前置不成立或假阳性；
   - 验收证据是否把“未执行”“跳过”或局部验证写成通过。
4. 输出 P0/P1/P2 清单，每条包含“断言 → 代码事实（file:line）→ 后果 → 最小修法”；确无发现时明确写“无承重错误”。
5. P0/P1 必须修复或由用户显式裁决豁免；修复后重新执行对应验证，再允许收口。

## 与方案对抗 Review 的区别

- 方案 Review 证伪“设计是否可行”。
- 完工代码 Review 证伪“实际实现是否忠实、测试证据是否有效”。

两者检查对象不同，不能互相替代。

## 建议验收标准

- 在相关 ritual 或与开发流程工具的衔接契约中加入该门禁；
- 提供可复用的完工代码对抗 Review 派工模板和必查清单；
- 验收证据能够记录 reviewer 结论、遗留项裁决和修复后的复验结果；
- 文档明确“独立上下文”与“共享工作区只读”的边界。
