# issue #5 · 明确冻结包内部按业务能力与任务证据包组织，避免时间/清理批次成为主导航

- 作者：yiqingnian28 · 2026-08-01T02:35:08Z · https://github.com/yiqingnian28/docloop/issues/5

## 问题

docloop 已明确 past 按迭代冻结、结算必须生成不超过 120 行的 summary.md、考古先读 summary 再精读史料，但没有明确冻结包内部应如何组织。

当 now 超预算触发提前结算时，执行者很容易按操作日期或文件类型归档，例如在旧迭代下建立“某日瘦身第 N 刀”，再分 plans、handoff、inbox、验收证据、接口样例。这样能降体积，却造成：

1. 同一业务能力的原始输入、CH、方案、证据和 handoff 被拆散；
2. 同一能力跨迭代形成多个历史孤岛；
3. “瘦身/清理批次”描述文档操作，不是长期业务导航；
4. 用户通常按“某模块为什么这样实现”考古，而不是按归档日期考古；
5. 只能依赖全仓搜索，无法实现“先 summary、再两跳内到证据”的渐进披露。

## 建议

明确双维度规则：

- 外层按迭代冻结，时间只承担审计和排序；
- 内层按业务能力/模块组织；
- 最小追溯单元按 T-### 形成任务证据包；
- CH 可集中在 changes 保持全局解析，但任务 manifest 必须链接对应 CH；
- 共享样例放 shared，由任务引用，不复制。

参考结构：

    past/YYYY-MM_i##_<迭代标题>/
    ├── summary.md
    ├── changes/
    ├── modules/
    │   ├── <能力A>/
    │   │   └── T-001_<任务>/
    │   │       ├── README.md
    │   │       ├── input/
    │   │       ├── plan.md
    │   │       ├── evidence.md
    │   │       └── handoff.md
    │   └── <能力B>/
    └── shared/

summary.md 建议按业务能力列出：完成任务、CH、当前 truth、证据包、未了事项，而不是只写日期流水。

同时建议禁止“第 N 次瘦身”“清理批次”“临时归档”或单纯日期目录成为长期主分类。提前结算应视为完整的小迭代结算，而不是批量搬文件。

## 可考虑的 lint

- 冻结包缺少 summary.md 时红灯；
- 出现明显操作型归档目录名时提示；
- summary 未覆盖冻结包中的 T/CH 时提示孤儿；
- 一个 T 的输入、方案、证据散落且无 manifest/README 串联时提示。

## 验收标准

- 从 summary 在两跳内到达任一任务的 CH、方案和验收证据；
- 从当前 truth 的 T/CH ID 能定位对应冻结任务；
- 查看某业务能力历史不需要先知道归档日期；
- 日常考古不需要全量加载 past 或做无边界全仓搜索。
