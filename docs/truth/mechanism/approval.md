# 报批草案表达契约

> 上级：[总述](README.md)。解决的问题（issue #3 / CH-006）：任务包过全部形式检查仍"合规但难读"——体积预算管得住尺寸，管不住认知结构。本章定义报批场景（实施方案 / 测试分析 / 验收方案草案）的表达契约与流程组合；操作细则见 skill 的 `rituals/approval.md`。

## 定位与分工

- 报批的**流程门禁**（何时出方案、批后才执行、证据验收）归 sdd-riper；docloop 只管**表达契约与落点**——两个问题域各只有一个主人，经目标项目 AGENTS.md 声明缝合（样例见 [sdd-riper.md](sdd-riper.md)）。
- 未装 sdd-riper 时本契约独立成立（裸跑兜底）。

## 表达契约：树 + 账双视图

同一份验收数据的两个视图——**树给人读**（自上而下 chunking 判断覆盖面），**账给机器对**（完备性对账）。正确性锚在"叶子集合 ⟷ covers 条目集合一一对应"，不锚在树的形状：形状可被装饰性嵌套伪装，属语义判定，lint 不测（D-014 分界）。

- **主阅读面 = 嵌套列表树**（不用 `├─` 字符画：省行数、可 diff、7c 检查直接适用）：
  - 中间节点（能力域 / 功能）只做分类命名，层级由 agent 按业务语义组织，机制不限形状；
  - 叶子三行版：「关注 / 验证 / 条目」各一行——关注与验证成对，条目挂 covers ID（`S-##.R-###`，行内代码，不计噪声信号）；
  - 未覆盖需求显式列为"缺口"分支（标注无裁决、无证据），不许静默消失。
- **附录 = 追溯矩阵**：叶子 → 自动化用例 → 执行证据（表格）——机器追溯不挤占主阅读面。
- **改造后形态用图不用大段文字**：模块结构 / 数据流 / 状态流用 mermaid（GitHub 原生渲染、文本可 diff、代码块不计 lint 信号）；一图一事、节点只放名词、不强制画——图管形状，树管验收。

## 叶子纪律（硬约束，已进 task.md 模板）

每个 covers 条目（无上游账本时自列需求点清单）↔ 至少一个功能叶子；叶子 = 关注 / 验证成对 + 挂条目 ID；验证点必须可由自动化测试或真实外部证据判定。

## 六问自检（提交草案前 agent 自查）

最终改成什么样 · 具体改哪些部分 · 每个需求点在树的哪个叶子 · 每个叶子由什么测试验证 · 哪些需求未覆盖 · 为什么测试全绿足以证明完成。

## 流程组合（不开新文档类）

报批 = 既有机制组合，机制不长个头：

```
起草任务包（总览 = 普通 T，Done Contract = "获批 + 内容分流完成"）
→ CH 裁决（获批 = 裁决通过，审批人 = 裁决人）
→ 分流：形态定论经 CH 改写进 truth · 树叶分进各实施 T（挂 covers）· 总览随迭代冻结进 past/
```

**分流不变量**：总览里"改造后是什么样"是 truth 的未来时，获批后必须分流——总览不许长期存活成第二真相。重方案（`plans/P-###` 独立文档类 + 预算档）挂起，实战疼点再议（CH-006）。

## lint 边界

不做树深度 / 关注-验证配对 / "全绿声明"检查——或属语义判定、或可被装饰性嵌套绕过（issue #3 自身反例：难读样例本有四层缩进），按 D-014 归 agent + 人；超长节点由 7c（含近阈值）覆盖。将来若加，唯一正确形态是"树叶 ⟷ covers ID 确定性对账"（孤儿检查同族），非形状检查。
