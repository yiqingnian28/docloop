# 任务包缺少实施报批与测试分析的表达规范，容易产出“合规但难读”的文档


### 问题现象

在一次复杂功能的实施报批中，我们使用 docloop 组织任务包。文档满足现有机制要求：

- 位于 `docs/now/`；
- 声明了 `reads` 和 `covers`；
- 写明目标、范围、实现依据、完成定义和验证证据；
- 没有超过任务包的行数与字节预算。

但第一版仍然很难由人快速审批：

- “获批后的实施”和“如何验收”混在大段文字中；
- 看不到改造后模块的整体形态及关键数据流；
- 测试内容按若干大类平铺，每类下面堆叠长句；
- 需求、功能场景、测试关注点、自动化用例和执行证据之间没有形成直观的证明链；
- 文档在结构、引用和体积上合规，却需要读者自行从文字中提炼“最终做成什么、具体怎么改、如何证明做对”。

这类文档能通过现有形式检查，但没有达到“人和 Agent 都能快速审查”的目标。

### 脱敏后的实际样例

以下样例已泛化，不包含原项目、公司、业务、接口、配置平台、数据、路径或内部编号。

#### 调整前：只有一层功能分类

```text
功能验收
│
├─ 模块形态与页面布局
│  ├─ 测试关注点：模块标题、布局、空态和内容隔离必须正确。
│  └─ 验证点
│     ├─ 标题只出现一次，卡片按配置顺序展示。
│     ├─ 空数据不产生空模块。
│     └─ 其他类型内容不混入当前模块。
│
├─ 数据来源与展示位置
│  ├─ 测试关注点：两个展示区域来自同一份配置，并正确排重。
│  └─ 验证点
│     ├─ 按优先级选择前若干项。
│     ├─ 不合格项触发后续项补位。
│     └─ 同一项不能在两个区域重复展示。
│
└─ 状态、失败与外部承接
   ├─ 测试关注点：覆盖完整状态和异常分支。
   └─ 验证点
      ├─ 不同状态下动作正确。
      ├─ 外部失败时不误报成功。
      └─ 客户端正确渲染并跳转。
```

这棵树形式上有节点，实质仍是“根节点 + 几个长段落分类”：

- 中间缺少真正的功能和场景层；
- 一个验证句承担多个需求；
- 无法一眼看出每个需求是否都有独立用例；
- 树枝只是替代了项目符号，没有降低认知负担。

#### 调整后：能力、功能、场景和验证逐层展开

```text
功能验收
│
├─ 页面与模块
│  ├─ 模块形态
│  │  ├─ 关注：单模块、单标题、固定布局。
│  │  └─ 验证：标题唯一；布局正确；无数据不建空模块。
│  ├─ 卡片内容
│  │  ├─ 关注：配置字段归属正确。
│  │  └─ 验证：各字段原样透传且不同卡片之间不串数据。
│  └─ 内容边界
│     ├─ 关注：不同类型内容相互隔离。
│     └─ 验证：目标内容进入新模块，其他内容保留在原容器。
│
├─ 数据来源与展示位置
│  ├─ 唯一来源
│  │  ├─ 关注：多个展示区域由同一份配置派生。
│  │  └─ 验证：条目身份和顺序均来自同一来源。
│  ├─ 优先选取
│  │  ├─ 关注：只选择满足条件的高优先级条目。
│  │  └─ 验证：数量充足时正确成组，数量不足时不拼不完整模块。
│  ├─ 排重
│  │  ├─ 关注：已经进入优先区域的条目不重复展示。
│  │  └─ 验证：按稳定身份排除；相同标题的不同条目不被误删。
│  └─ 补位
│     ├─ 关注：不合格条目不能占位置。
│     └─ 验证：规则不命中、配置非法或技术不可用时，后续合格条目补位。
│
├─ 生命周期
│  ├─ 前置条件未满足
│  │  ├─ 关注：不可执行主要动作。
│  │  └─ 验证：只给出引导，不调用主要业务链路。
│  ├─ 可执行
│  │  ├─ 关注：只有合法状态能够发起操作。
│  │  └─ 验证：调用当前条目的业务链路并返回可判定结果。
│  ├─ 终态
│  │  ├─ 关注：终态不可重复操作且不消失。
│  │  └─ 验证：所有终态均禁用、保留条目并给出后续信息。
│  └─ 周期恢复
│     ├─ 关注：跨过真实周期边界后重算资格。
│     └─ 验证：时间边界前后状态变化与规则一致。
│
└─ 失败与外部承接
   ├─ 外部失败
   │  ├─ 关注：不伪造成功、不吞掉条目。
   │  └─ 验证：返回普通失败或不可用状态，保留条目并支持正确重试。
   ├─ 客户端渲染
   │  ├─ 关注：客户端正确消费服务端结构和状态。
   │  └─ 验证：布局、禁用态、失败提示均与服务端结果一致。
   └─ 未纳入能力
      ├─ 关注：范围外需求不能被测试全绿掩盖。
      └─ 验证：没有后续裁决和真实证据时明确标记未覆盖。
```

调整后，文档形成了清晰的阅读和验收路径：

```text
需求
→ 业务能力
→ 具体功能
→ 状态、规则或异常场景
→ 测试关注点
→ 可判定验证点
→ 自动化用例
→ 真实执行结果
```

实际案例最终拆成多级能力域与多个功能叶子，每个叶子都有一组“关注 / 验证”。读者可以先核对功能树是否覆盖需求，再核对每个叶子是否有测试，最后用全绿结果完成验收。

### 可能原因

1. docloop 的核心定位是管理知识的位置、流动和老化，而不是规定单个任务如何表达。这个边界本身合理，但在没有配套细则时，任务包容易退化成普通任务文档。
2. 当前 [`task.md`](https://github.com/yiqingnian28/docloop/blob/main/skills/docloop/references/templates/task.md) 只要求目标、范围、Done Contract、实现依据、Checkpoint、验证记录和偏差记录，没有“实施报批方案”的专用结构。
3. Done Contract 要求说明完成标准和证据，但没有规定如何把需求拆成可逐项验收的功能树，也没有要求每个功能叶子对应可观察的验证结果。
4. 行数和字节预算是有效的上下文约束，但缺少认知复杂度约束。Agent 容易通过压缩段落满足体积预算，却让单个节点承载过多含义。
5. 现有 lint 能检查目录、体积、链接、腐烂、孤儿条目等问题，但不能识别“树只有一层”“节点仍是长段落”“需求无法逐叶验收”等可读性问题。
6. [`SKILL.md`](https://github.com/yiqingnian28/docloop/blob/main/skills/docloop/SKILL.md) 把任务推进与证据验收交给 sdd-riper；但 docloop 又允许单独运行。单独运行时，目前缺少最低限度的实施报批表达契约。

### 改进建议

建议不扩大 `SKILL.md` 常驻内核，而是通过渐进披露增加一个专用参考模板，例如：

```text
skills/docloop/references/templates/approval-plan.md
```

当用户要求“实施方案、实现草案、报批计划、测试分析或验收方案”时，由 skill 路由到该模板。

模板建议至少包含以下部分：

1. **本次请批准什么**
   - In / Out；
   - 待裁决项；
   - 什么条件下才能开始修改代码。
2. **改造后是什么样**
   - 页面、模块或接口形态图；
   - 关键数据流或状态流；
   - 只保留影响审批的关键说明。
3. **准备怎么实施**
   - 按工作包拆分改造；
   - 每个工作包说明目标、主要代码面和明确不做；
   - 外部依赖和上线门单列。
4. **测试分析与用例**
   - 按“能力 → 功能 → 场景”自上而下拆解；
   - 中间节点只做分类，不写长段落；
   - 每个功能叶子必须同时包含“关注”和“验证”；
   - 验证点必须能够由自动化测试或真实外部证据明确判定；
   - 配置内容正确性与系统逻辑正确性分开；
   - 未纳入本批的需求作为显式缺口保留，不能静默消失。
5. **验收证明链**
   - 主阅读面先展示可读的功能树；
   - 机器追溯信息可放附录或单独矩阵；
   - 最终能建立“需求点 → 功能叶子 → 自动化用例 → 执行证据”的对应关系。

可以考虑增加轻量提示或 lint warning，而不是一开始做强制红灯：

- 测试分析只有“根节点 + 一层分类”时提示结构可能过平；
- “关注”和“验证”数量不一致时提示叶子不完整；
- 单个树节点超过一定长度时提示可能仍是段落搬运；
- Done Contract 声称“测试全绿即完成”，但没有逐需求测试分析时提示证明链不完整；
- 任务接近字节上限且存在大量长节点时，建议压缩措辞或拆出受控附件，而不是继续堆叠段落。

### 期望结果

使用者只提供需求材料并要求生成“实施报批草案”时，Agent 第一次产出的任务包就应让审批人快速回答：

1. 最终会改成什么样？
2. 具体准备改哪些部分？
3. 原需求的每个功能点在哪里？
4. 每个功能点由什么测试验证？
5. 哪些能力仍未覆盖？
6. 为什么测试全绿足以证明任务完成？

同时继续保持 docloop 现有优势：三层知识模型、CH 裁决、来源追溯、上下文预算和迭代冻结。

### 非目标

- 不要求 docloop 取代 sdd-riper 的完整任务推进机制；
- 不建议所有简单任务都强制画复杂图；
- 不放松现有体积预算和变更治理；
- 不强制所有项目使用同一种业务术语或同一种图形语法；
- 不把机器追溯编号重新放回人的主阅读路径。
